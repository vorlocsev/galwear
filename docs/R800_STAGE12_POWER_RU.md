# Этап 12: Exynos 9110 — диагностика сна и исправление callback

Вся работа ведётся только в `vorlocsev/galwear` в ветке
`development/r800-stage12-power-audit-20261124`. Исходный репозиторий,
`main`, новые PR, релизы, реальные часы и их содержимое **не затронуты**.

## Что обнаружено в коде ядра

В `src/kernel/r800-wearos.patch` обработчик `bbd_resume()` проверял
`pssp_driver->driver.pm->suspend`, после чего вызывал
`pssp_driver->driver.pm->resume`.

Это несовпадение проверяемого и вызываемого callback: при наличии suspend
и отсутствии resume возможен вызов нулевого указателя. Исправлена
проверка на существование **resume** и добавлена проверка самого
`pssp_driver`. В `bbd_suspend()` сохранена проверка **suspend**.

Проверка формата патча `git apply --numstat` и синтетические тесты
проходят; **патч ещё не применялся к настоящему Linux 4.19 source tree,
ядро не компилировалось и аппаратная причина зависаний не доказана**.

## Текущая политика питания — без изменения по умолчанию

- Без флага `android/SLEEP`: helper удерживает `r800helper` wakelock,
  препятствующий полному системному suspend (если ядро успешно приняло блокировку).
- Без флага `android/CPUIDLE_DEEP`: состояние `cpuidle/state1`
  отключено для обоих ядер.
- Эти два режима независимы; включение глубокого CPU idle не равнозначно
  полному выключению доменов питания.
- Исходный код содержит экспериментальные записи
  `r800_sleep_pd_off` и `r800_dispaud_sleep_off`; сами параметры
  остаются аппаратно непроверенными в форке.

Данных для включения глубокого сна по умолчанию **нет**.

## Новый сборщик `installer/r800_power_audit.py`

Работает **только на чтение**. Не открывает сокеты, не вызывает команды
`reboot`, `suspend`, `sysrq`, не изменяет sysfs и не управляет watchdog.

Снимок из заранее предоставленной локальной копии диагностических
узлов (например, в отдельной тестовой файловой системе):

```sh
python3 installer/r800_power_audit.py snapshot \
  --root /path/to/read-only-sysfs-fixture \
  --output before.json
```

Повторить для второго диагностического набора, затем сравнить:

```sh
python3 installer/r800_power_audit.py compare \
  --before before.json --after after.json --output power-comparison.json
```

Скрипт умеет читать ограниченные показатели:
`/proc/uptime`, `/sys/power/wakeup_count`, счётчики `cpuidle/state1`
для двух ядер, состояние экспериментальных параметров Exynos PD/ABOX,
основные численные данные батареи и численные счётчики
`/sys/kernel/debug/suspend_stats`. Наличие `r800helper` wakelock
показывается только как boolean.

**Не собираются** сырые kernel logs, списки других wakelocks, адреса,
IMEI, серийные номера, `/proc/cmdline` и содержимое заводских разделов.
При недоступном узле отчёт отмечает поле как `unavailable`, не
выдумывая значение. Сравнение после изменения uptime или режима
выдаёт предупреждение; увеличение счётчика само по себе не доказывает
ни успешного, ни стабильного пробуждения.

### Таблица исследовательских режимов (только для будущих испытаний)

| Сценарий | SLEEP | CPUIDLE_DEEP | Цель |
| --- | --- | --- | --- |
| A | off | off | Контрольный консервативный режим |
| B | off | on | Изолировать глубокий CPU idle |
| C | on | off | Изолировать полный system suspend |
| D | on | on | Комбинированный режим, самый высокий риск |

Ни один из B/C/D **не рекомендуется запускать на часах**, пока не
подтверждены read-only диагностический доступ и путь восстановления.
Зависание около 16 минут после глубокого сна описано в helper, но
истинная причина всё ещё неизвестна. Не интерпретировать 3 успешных
пробуждения как долгосрочную стабильность.

## Офлайн-приёмка

```sh
python3 -m py_compile installer/r800_power_audit.py
sh -n payload/android-helper.sh
git apply --numstat src/kernel/r800-wearos.patch >/dev/null
python3 -m unittest discover -s tests -p 'test_stage12_power.py' -v
python3 -m unittest discover -s tests -p 'test_*.py' -v
```

Программные проверки подтверждают только свойства тестовых файлов и
правильность защитной логики. Следующий аппаратный блокер:
собрать **реальные, разрешённые журналы и проверенную процедуру
восстановления**, затем воспроизвести проблему с конкретным SHA ядра.
