# SM-R800: откат отдельных power domains (NON-RELEASE)

База: development/r800-pmucal-suspend-guard-20261125. Только форк.
В Linux 4.19 syscore_suspend не вызывает resume у своего неуспешного callback:
drivers/base/syscore.c, list_for_each_entry_continue. Поэтому локальный откат
выполняется до возврата ошибки из r800_pd_syscore_suspend.

- CAL control проверяет одновременно код результата и точный статус 0/1.
- Домен с неизвестным статусом не отключается; отсутствующий запрошенный
  домен и неподдерживаемая маска приводят к отмене.
- Попытка выключения фиксируется до CAL; rollback включает DISPAUD первым,
  остальные домены в обратном порядке. Ошибка одного не останавливает попытки
  восстановления остальных.
- Сохранённый CTRL_OPTION восстанавливается только при подтверждённом
  включении домена, с readback; отдельно обработан сбой записи до power-off.
- Любой сбой в пути abort (включая занятый ABOX) консервативно запрещает
  дальнейший suspend до перезагрузки. Ошибка восстановления после resume
  также блокирует следующий suspend.
- Отсутствие DISPAUD больше не отключает регистрацию всего guard.

Проверка контекста изменённой diff-секции выполнена против точного SHA
50db73fc799f20a7120a8b5f653b16cc123d856f. Добавлены восемь статических unittest
и проверены их условия; запуск Python unittest/CI и сборка не подтверждены.
Сами статические проверки не моделируют реальное поведение CAL, SMC или MMIO.

Остаётся проверить pmucal_local_is_enabled: базовая реализация игнорирует
результат pmucal_rae_handle_seq(status,...), так что точный статус 0/1 сам по
себе не доказывает успешный доступ к регистрам. Проверить abort между
syscore и PSCI, а также повторное включение домена после частичного отказа.
Нет доказательств безопасного отката аппаратного состояния. Глубокий сон
не включать; safe_to_flash=false. Без PR, firmware, изменений main/upstream.
