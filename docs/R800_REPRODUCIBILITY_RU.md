## Новый инструмент `build/r800_reproducibility_audit.py`

Имеет два режима:

- `emit`: **только после успешной** компиляции `Image` и проверки
  CPIO записывает JSON с точными SHA-256 ядра, конфигурации, патча,
  CPIO и ELF `/init`; исходным commit ядра и Galwear;
  идентификатором использованного контейнера, версиями Clang/LLD,
  GitHub run ID и attempt. Настоящие образы не загружает в артефакты.
- `compare`: сравнивает JSON **двух разных** запусков. Совпадение
  всех обязательных полей выдаёт `TWO_RUN_HASH_MATCH`, несовпадение
  — `REJECT_MISMATCH` с именами полей, но без секретов и бинарников.

Одного JSON **недостаточно**: его статус
`ONE_BUILD_EVIDENCE_ONLY` всегда оставляет
`reproducibility_proven=false`.

Два совпадающих SHA тоже не доказывают полной воспроизводимости:
пакеты окружения (кроме Clang/LLD 19.1.4) не закреплены целиком,
нет независимого подтверждения подлинности Samsung S-Boot,
подписи или возможности восстановления. Сравнение ставит
`two_run_byte_identity_observed=true`, но
`general_reproducibility_proven=false` и `safe_to_flash=false`.

## Как получить данные для сравнения

Текущий workflow
`.github/workflows/r800-embedded-initramfs-build.yml`
после успешного шага сборки записывает
`r800-image-repeatability.json` и публикует **только этот JSON**
в составе `r800-embedded-initramfs-evidence-only`.

Тест двух независимых запусков требует скачать их отчёты
в локальную временную папку без скачивания `Image`, CPIO или ELF.
Затем:

```sh
python3 build/r800_reproducibility_audit.py \
  --output repeatability-comparison.json compare \
  --first evidence-from-run-1.json \
  --second evidence-from-run-2.json
```

Выходной код `0` — только для совпадающих отчётов с разными
run ID/attempt; `2` — для неверной схемы, неизвестной версии
компилятора, отсутствующих/неправильных хешей, одинаковых запусков
или любого различия в обязательных полях.

## Как устроен запуск в GitHub Actions

Перед компиляцией workflow выполняет `docker pull alpine:3.21`,
записывает точный Docker **image ID**, после чего запускает
`docker run --pull=never`. Так проверяется, какой образ
использовался в конкретном CI-run; совпадение имени тега само по себе
не считается доказательством идентичности.

Сборка по-прежнему:

1. Загружает точный SHA ядра в изолированный runner.
2. Проверяет `git apply --check`.
3. Собирает экспериментальный `/init`.
4. Встраивает `/init` через временный `CONFIG_INITRAMFS_SOURCE`.
5. Проверяет CPIO и байтовое совпадение `/init`.
6. Записывает контрольные суммы; **не публикует** бинарные файлы.
7. Не запускает прошивку и не подключается к часам.

## Подтверждённая побайтовая повторяемость минимального `/init`

GitHub Actions №45490355733 завершился **PASS**. Два независимых
GitHub runner (`a` и `b`) собрали статический AArch64
`src/initramfs/init.c` с Clang/LLD 19.1.4. Третий job проверил
совпадение SHA-256 исполняемого `/init`, размера,
SHA-256 исходного `init.c`, коммита Galwear и Docker image ID.
Выгружались только JSON с хешами; сами бинарники не публиковались.

Проверенное утверждение: **в двух этих независимых сборках `/init`
побайтово совпал**. Оно НЕ относится к готовому `Image`, ядру со
встроенным initramfs, NZIT или прошивке Wear OS.

Workflow:
`.github/workflows/r800-init-repeatability.yml`.

```sh

```

Проверяются отказы при отличающемся `Image`, CPIO, `.config`,
Docker image ID, исходном SHA, повторном использовании одного run ID,
некорректных флагах безопасности и отсутствующей проверке CPIO.

До дальнейших этапов: подтвердить успешную объединённую сборку,
получить два независимых JSON и сравнить их, затем проверить
read-only загрузочный сценарий без доступа на запись к eMMC.
